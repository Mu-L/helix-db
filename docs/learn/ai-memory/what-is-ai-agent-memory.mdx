AI agent memory is the infrastructure that lets an agent built on a large language model
(LLM) keep information beyond a single model call: what a user told it, what happened in
earlier sessions, and how it should carry out recurring tasks. Because the model itself
is stateless, memory lives in an external store that the agent writes to after an
interaction and reads from before the next one. A useful memory layer does more than
save transcripts. It extracts durable facts, keeps them current, forgets what is stale
or deleted, and recalls only the relevant, permitted subset for each request.

## Why is a context window not memory?

The context window is the text a model can read in one call. It works like working
memory: everything the model knows about the current task has to be in it, and it is
gone when the call ends. Treating it as long-term memory breaks down for several
reasons:

- **It resets.** A new session starts empty unless something outside the model puts
  earlier information back.
- **It is bounded and priced per token.** Replaying every past conversation grows cost
  and latency with each turn, and eventually stops fitting.
- **It has no notion of truth over time.** If a user said one thing last month and the
  opposite today, a transcript contains both, and the model has to guess which is
  current.
- **It is not scoped.** Nothing in a raw prompt records who owns a fact, where it came
  from, or whether it may be shown to this user.
- **More text is not always better context.** Models do not use every part of a long
  prompt equally well, so a focused set of relevant facts often produces better answers
  than a full history.

Larger context windows make short-term memory roomier, but they do not replace a system
that decides what to keep, what changed, and what to retrieve.

## What types of memory do AI agents use?

Agent memory is usually described with terms borrowed from cognitive psychology.
Short-term memory covers what the agent is working with right now; long-term memory
persists across sessions.

| Type | Horizon | What it holds | Example |
| --- | --- | --- | --- |
| Working memory | One model call | The prompt: instructions, recent turns, retrieved context | The assembled context for the current reply |
| Conversation history | One session | Recent messages in the current conversation | The last few turns of a support chat |
| Episodic memory | Long-term | Specific past events, with when and where they happened | "The user reported a failed CSV export in last week's session" |
| Semantic memory | Long-term | Facts and preferences, independent of when they were learned | "The user prefers invoices as PDF attachments" |
| Procedural memory | Long-term | How to do things: learned workflows and rules | "For this account, check billing status before issuing a refund" |
| User profile | Long-term, derived | A condensed summary of stable facts and current focus | "Finance admin, moving the team to annual billing this quarter" |

The difference between **episodic and semantic memory** matters in practice. Episodes
answer "what happened"; semantic facts answer "what is true now." Agents often derive
semantic facts from episodes, for example inferring a preference from several
conversations, and keep a link back to those episodes as evidence. The **user profile**
is not a separate source of truth. It is a summary maintained from long-term memories so
the agent can load broad context cheaply on every request.

## How does the memory lifecycle work?

A memory system is a loop. Every interaction can add, change, or remove memories, and
every request reads from the result.

```mermaid
flowchart LR
    ingest["Ingest<br/>messages, documents, events"] --> extract["Extract<br/>candidate facts"]
    extract --> dedupe["Deduplicate<br/>against existing memories"]
    dedupe --> update["Update or version"]
    update --> store[("Memory store")]
    forget["Forget<br/>expire, decay, delete"] --> store
    store --> recall["Recall<br/>scoped, current, relevant"]
    recall --> agent["Agent response"]
    agent --> ingest
```

1. **Ingest.** Collect raw input: conversation turns, uploaded documents, tool results,
   and application events.
2. **Extract.** Turn raw input into atomic, self-contained facts. A reply such as "next
   Tuesday" only means something together with the question before it, so the
   extractor needs recent conversation context and the current date.
3. **Deduplicate.** Compare each candidate with existing memories, by meaning and by
   exact terms, so the same fact is not stored many times.
4. **Update and version.** When a fact changes, write a new version and mark the old one
   as superseded instead of overwriting it. History stays available for audits and for
   questions about what changed.
5. **Forget.** Expire time-bound facts, let low-value episodes decay, and delete what a
   user or policy asks to remove.
6. **Recall.** Retrieve the memories this user may see, that are still current, and that
   are relevant to the request, then assemble them into context.

The guide to [building long-term memory](/learn/ai-memory/long-term-memory-for-ai-agents)
walks through each step as a concrete architecture.

## What infrastructure does a memory layer need?

Each lifecycle step places a different demand on storage and retrieval.

| Requirement | Why it matters | Typical mechanism |
| --- | --- | --- |
| Identity and tenancy | Memories belong to a user, team, or organization and must never leak across them | Scope keys on every record, indexed filters, per-tenant indexes |
| Relationships | Facts connect to people, topics, sources, and earlier versions | Graph edges that queries can traverse |
| Semantic recall | Users rephrase; "my flight" should find "the trip to the conference" | Vector search over embeddings |
| Exact recall | Names, IDs, error codes, and rare terms blur in embeddings | Full-text search, typically ranked with BM25 |
| Recency and lifecycle | Only current, undeleted, unexpired facts belong in context | Timestamps and flags with equality and range indexes |
| Provenance | The agent must cite sources, debug bad memories, and honor deletion of a source | Links from each memory to the messages or documents it came from |

Many teams assemble these from several systems, such as a relational store for records,
a vector store for embeddings, and a search engine for keywords. That works, but the
application then has to keep them consistent. A memory deleted in one system can still
surface from another, and a permission filter applied after a similarity search can
remove every result or, if it is forgotten, leak one.

## How HelixDB supports agent memory

HelixDB is an open-source graph database with native vector search and BM25 full-text
search, so the requirements above can be met in one labeled property graph:

- **Properties with indexes** hold tenant scope, identity, and lifecycle fields such as
  `isLatest`, `validTo`, `deletedAt`, and `expiresAt`. Equality and range
  [secondary indexes](/database/helix-db/query-guides/secondary-indexes) make them fast
  filters.
- **Edges** record provenance, categories, entities, version updates, and associations.
- **Vector search** handles deduplication and paraphrase recall, and **BM25** handles
  exact names, IDs, and rare tokens. Both index types can be
  [partitioned by tenant](/database/helix-cloud/operate/multi-tenancy).
- **A profile node** holds stable user context that the agent loads on every request.

The recall pattern is to build the visible candidate set first with a graph traversal,
then run [prefiltered](/database/helix-db/query-guides/prefiltering) vector and BM25
search inside it, so a memory outside the set is never returned. Each request runs as
one ACID transaction, so the traversal and both searches read the same snapshot. The
application computes embeddings and fuses the vector and BM25 result lists, because
HelixDB has no built-in rank-fusion operator.

## Frequently asked questions

### What is the difference between short-term and long-term memory for AI agents?

Short-term memory is what the model can see during the current task: the context window
and the recent conversation. Long-term memory persists across sessions in an external
store and includes episodic, semantic, and procedural memories. The agent moves
information between them by writing extracted facts to long-term memory and recalling a
relevant subset into the context window.

### Is agent memory the same as RAG?

They share retrieval techniques but differ in what they retrieve. Retrieval-augmented
generation (RAG) typically reads from a document collection that changes independently
of the agent. Memory is written by the agent from its own interactions, changes as facts
are corrected, and is scoped to a user or team. Many systems combine the two and link
each memory to the source passage it came from.

### Can a vector database alone serve as agent memory?

A vector index covers semantic recall, which is one requirement out of several. On its
own it cannot tell a current fact from a superseded one, enforce who owns a memory,
reliably match exact identifiers, or explain where a fact came from. Those need
properties, lifecycle filters, keyword search, and relationships alongside the vectors.

### How should an AI agent forget?

Most systems prefer soft deletion: mark a memory as deleted or superseded and exclude it
from every recall path, which keeps an audit trail and allows recovery. Time-bound facts
get an expiry, and low-value episodes can decay based on age and use. Physical deletion
is reserved for cases where a user request or a retention policy requires it.

### Do larger context windows remove the need for memory?

No. A larger window lets more text into a single call, but the model is still stateless
between sessions, cost and latency grow with prompt size, and nothing in the window
resolves which of two conflicting facts is current. Memory decides what to keep and what
to retrieve; the context window is where the retrieved result goes.
