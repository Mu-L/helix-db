A distance metric is the formula a vector search uses to decide how close two embeddings
are. Cosine distance compares direction and ignores length, Euclidean distance measures
the straight-line gap between two points, and Manhattan distance sums the gap along each
dimension. The right choice is usually the metric your embedding model was trained for,
which its provider normally documents.

## The three metrics

For two vectors `a` and `b` with `n` dimensions:

```text
cosine similarity   = (a · b) / (|a| × |b|)
cosine distance     = 1 − cosine similarity

Euclidean (L2)      = sqrt( Σ (aᵢ − bᵢ)² )

Manhattan (L1)      = Σ |aᵢ − bᵢ|

dot product         = Σ aᵢ × bᵢ
```

| Metric | Measures | Sensitive to vector length? | Typical use |
| --- | --- | --- | --- |
| Cosine | The angle between vectors | No | Text and sentence embeddings |
| Euclidean (L2) | Straight-line distance | Yes | Embeddings where magnitude carries meaning, image and spatial features |
| Manhattan (L1) | Sum of per-dimension differences | Yes | Sparse or high-dimensional features where large single-dimension gaps should not dominate |
| Dot product | Alignment scaled by length | Yes | Models trained to score with an inner product |

Similarity and distance point in opposite directions: a higher cosine similarity means
a smaller cosine distance. Search systems usually sort by distance, closest first.

## A worked example

Take a query vector `a = (1, 0)` and two stored vectors, `b = (0.6, 0.8)` and
`c = (2, 0)`.

| Pair | Cosine similarity | Euclidean | Manhattan |
| --- | --- | --- | --- |
| `a`, `b` | 0.6 | 0.894 | 1.2 |
| `a`, `c` | 1.0 | 1.0 | 1.0 |
| Nearest to `a` | `c` | `b` | `c` |

`c` points in exactly the same direction as `a` but is twice as long. Cosine ignores
the length, so `c` is a perfect match. Euclidean counts the extra length as distance,
so `b` wins. The metrics disagree because the vectors have different lengths.

## When do the metrics agree?

When every vector is normalized to unit length, cosine and Euclidean distance produce
the same ranking. For unit vectors, the squared Euclidean distance equals
`2 − 2 × cosine similarity`, so ordering by one orders by the other. The dot product of
unit vectors also equals their cosine similarity.

Manhattan distance does not have this property: it can rank normalized vectors
differently from cosine and Euclidean distance.

<Tip>
Many embedding models return normalized vectors. If yours does, cosine is a safe
default, and switching to Euclidean distance would not change the order of results.
</Tip>

## How to choose a distance metric

1. **Use the metric the embedding model was trained for.** Model documentation usually
   says whether to compare its embeddings with cosine similarity, dot product, or
   Euclidean distance. Matching it gives the rankings the model was optimized to
   produce.
2. **Check whether the vectors are normalized.** If they are, cosine, Euclidean, and dot
   product rank results the same way, and the choice matters little.
3. **Keep one metric per index.** Every vector in an index, and every query vector, must
   come from the same model and be compared with the same metric. Changing the model or
   metric means re-embedding and rebuilding the index.
4. **Evaluate on your own queries.** When in doubt, measure recall and relevance on a
   sample of real questions with each candidate metric.

## How HelixDB supports distance metrics

Each HelixDB [vector index](/database/helix-db/query-guides/vector-indexes) declares one
metric, cosine, Euclidean, or Manhattan, and a fixed dimension. Every stored embedding
and every query vector must match that dimension exactly.

- **Results come back closest first.** Hits carry a `$distance` value that you can
  return in a projection.
- **Cosine needs a non-zero vector.** A cosine vector with zero length has no direction,
  so HelixDB rejects it with the `zero_norm_cosine_vector` error code.
- **Dot product is not a separate metric.** For a model that recommends dot product on
  normalized embeddings, use cosine, which ranks those vectors the same way.

The application computes embeddings, and HelixDB stores and indexes them on nodes or
edges. See [What is vector search?](/learn/vector-search/what-is-vector-search) for how
nearest-neighbor search works.

## Frequently asked questions

### Is cosine similarity better than Euclidean distance?

Neither is better in general. Cosine compares direction only, which suits most text
embeddings. Euclidean distance also accounts for length. For normalized vectors they
rank results identically.

### Should I normalize my embeddings?

Normalize when your model's documentation recommends it or when you want vector length
to stop influencing results. After normalization, cosine, Euclidean, and dot product
give the same ordering.

### When is Manhattan distance useful?

Manhattan distance adds up absolute differences per dimension, so one very large
difference affects it less than it affects Euclidean distance. It is sometimes preferred
for sparse or very high-dimensional features. Test it against your own data before
choosing it.

### What is the difference between dot product and cosine similarity?

Cosine similarity is the dot product divided by both vectors' lengths. For unit-length
vectors they are equal. For vectors of different lengths, the dot product also rewards
longer vectors.
